Qué es Anvil

Anvil es un secuenciador de test: corre secuencias de pasos contra equipo real, reintenta los que fallan y reporta el resultado. Como NI TestStand, pero sin su coste (~$4,310/seat/año), sin LabVIEW atado, sin deployment monolítico, sin reportes rígidos.

La idea central, copiada de TestStand, es que el secuenciador es el host que orquesta, no un runner que ejecuta tu código. La secuencia es datos (YAML diffable, versionado en Git), no un binario opaco. Cada paso se invoca por gRPC por su nombre — nunca con una llamada directa — lo que aísla los pasos entre sí y deja la puerta abierta a escribirlos en cualquier lenguaje.

Secuencia = datos

YAML diffable, versionado en Git. El motor lo recorre sin saber qué hace cada paso. No un .seq binario.

Pasos en cualquier lenguaje

El adapter es gRPC. No hay código de pegamento en el motor ni runtime de vendor atado. Rust, Python, C, Zig, lo que sea.

Motor en WASM

Portable y aislado: ./anvil secuencia.yaml sin instalador. Sandbox real, JIT a nativo, determinismo para reintentos reproducibles.

Características

Semántica Setup → Main → Cleanup

El Main corta en el primer fallo; el Cleanup corre siempre — un equipo que se quedó encendido es peor que una secuencia que falló.

Reintentos por paso

Cada paso declara cuántos intentos admite. El número de intento llega al paso, que puede simular fallos transitorios.

Límites como datos first-class

El límite vive en el YAML, no en el código del paso. El paso mide; el motor evalúa el umbral declarado (ADR-0008). Cambiar umbrales por lote no toca la secuencia.

Variables y expresiones

Scopes Locals / Parameters / FileGlobals. Expression engine estilo Julia (cortocircuito, sin truthiness). Precondición por paso, asignación de resultados, pasos statement locales sin gRPC.

Subsecuencias (sequence call)

Invoca otra secuencia como un paso, con Parameters entrada/salida by-reference como TestStand. Inline por nombre o en archivo aparte por path. Detección de ciclos al cargar.

ResultSink desacoplado

Consola, JSON y CSV de serie (estilo OpenTAP ResultListener). SQLite/STDF post-MVP. Reintento de IO ante fallos transitorios.

Routing multi-endpoint

ejecutores: en el YAML + --ejecutor por CLI. Un paso lo atiende el ejecutor embebido (de serie), un .wasm cargado por path, o un servidor gRPC en otra máquina — el motor no distingue.

Cargador de .wasm por path

El modelo .vi de TestStand en WASM: compila tu paso en Rust (una función run, interfaz WIT anvil:paso), referéncialo por path en el YAML y ejecuta. El host lo puentea a gRPC — el motor no distingue. Sin recompilar el secuenciador.

Un binario

Descarga anvil y corre. wasmtime va embebido; los dos guests WASM (motor + ejecutor) van dentro. Sin instalar runtimes. Sin dependencias.

Arquitectura

Anvil hospeda wasmtime como librería y orquesta dos guests WASM — motor (recorre la secuencia) y ejecutor (despacha pasos por nombre) — en sandboxes separados, hablando gRPC por loopback TCP restringido. El motor no sabe qué hay detrás de cada endpoint: ejecutor embebido, .wasm cargado por path, o servidor gRPC en otra máquina.

La frontera gRPC motor↔ejecutor es real (aislamiento motor-side). El contrato es paso.proto: service EjecutorPasos { rpc Invoca(PeticionPaso) returns (ResultadoPasoProto) } — un método, unaria. No se rompe sin un ADR (RNF-05).

Inicio rápido

Anvil es un binario: lo descargas y corres. Por dentro hospeda wasmtime y los dos guests WASM en sandbox, hablando gRPC por loopback. No necesitas instalar nada. Para probar antes de compilar: clona el repo y compila (abajo).

1. Escribe tu paso en Rust

Un paso es un componente WASM que exporta la función run (interfaz WIT anvil:paso). No sabes de gRPC, no sabes de protobuf, no sabes de Anvil: es una función. Necesitas cargo y una sola herramienta extra: 

cargo install cargo-component --locked

Estructura del proyecto (hola/):

hola/
  Cargo.toml          # [lib] crate-type = ["cdylib"], deps: wit-bindgen-rt
  wit/anvil-paso.wit  # el contrato (lo copias, 12 líneas)
  src/lib.rs          # tu función run
# wit/anvil-paso.wit — el contrato de un paso
package anvil:paso@0.1.0;
interface paso {
  record resultado {
    estado: string,        // "paso" | "fallo" | "error"
    mensaje: string,
    valor-medido: option<f64>,
  }
  run: func(nombre: string, intento: s32) -> resultado;
}
world anvil-paso { export paso; }
# src/lib.rs — tu paso es una función
#[allow(warnings)]
mod bindings;
use bindings::exports::anvil::paso::paso::{Guest, Resultado};

struct Component;

impl Guest for Component {
    fn run(nombre: String, intento: i32) -> Resultado {
        Resultado {
            estado: "paso".to_string(),
            mensaje: format!("hola {nombre} (intento {intento})"),
            valor_medido: Some(4.2),
        }
    }
}

bindings::export!(Component with_types_in bindings);

2. Compílalo a .wasm

# en hola/ — genera target/wasm32-wasip1/debug/hola.wasm
cargo component build

3. Decláralo en una secuencia

# secuencia.yaml
nombre: mi_secuencia
ejecutores:
  - { nombre: hola, tipo: wasm, path: ./hola.wasm }
main:
  - nombre: mundo
    ejecutor: hola
    reintentos: 1
    limite: { tipo: rango, min: 4.0, max: 5.0 }

4. Ejecuta

# Anvil spawnea el puente, que carga tu .wasm y lo traduce a gRPC.
# El motor evalúa el límite (4.2 está dentro de [4.0, 5.0]) y reporta.
./anvil secuencia.yaml
=== mi_secuencia: paso ===
  [paso] mundo: hola mundo (intento 1)

Compilar Anvil (build desde source)

# 1. Guests WASM (motor + ejecutor) — workspace del core
cargo build --target wasm32-wasip2 -p motor -p ejecutor_pasos

# 2. Puente (workspace aparte; wasmtime + tonic se compilan aquí)
cargo build --manifest-path packaging/anvil-puente-wasm/Cargo.toml

# 3. Host nativo (embebe los guests y el puente)
cargo build --manifest-path packaging/anvil-host/Cargo.toml
# → packaging/anvil-host/target/debug/anvil

CLI

anvil <secuencia.yaml> [--json <r>] [--csv <r>] [--limits <r>] [--ejecutor nombre=host:puerto]
  • Consola siempre (reporte textual, stdout limpio).
  • --json / --csv: vuelcan a fichero.
  • --limits: sidecar de límites por nombre de paso (RF-30).
  • --ejecutor nombre=host:puerto: re-apunta un ejecutor sin tocar el YAML (R&D vs. fábrica).
  • --solo-loopback: rechaza cualquier grpc no-loopback (CI/paranoia).

Roadmap

Hitos de lo más cercano a lo más lejano. Lo ya hecho se marca; el resto es propuesta de orden, no compromiso de fecha.

M0 — Prototipo ✓

Motor + ejecutor gRPC sobre wasi-grpc. Semántica Setup→Main→Cleanup. Reintentos. Reporte textual.

M1 — Secuencia como datos ✓

Schema YAML de DefinicionSecuencia + cargador. El motor no cambia.

M2 — ResultSink ✓

Consola/JSON/CSV desacoplado (estilo OpenTAP). SQLite aplazado.

M3 — Límites como datos ✓

Límites high/low/comparación first-class. Property loader sidecar. El motor evalúa.

M4 — Variables y control de flujo ✓

Expression engine (Julia), scopes, precondición, disable, pause_on_fail, statement local.

M4b — Sequence call ✓

Subsecuencias inline y por path. Parameters by-reference. Detección de ciclos.

M5-ext.1 — Routing multi-endpoint ✓

ejecutores: en YAML + override --ejecutor. Relajación acotada del loopback.

M5-ext.2 — Cargador .wasm por path ✓

Modelo .vi de TestStand en WASM. Tu paso es una función run (WIT anvil:paso); el host lo puentea a gRPC. Sin clonar el repo.

M5-base — Process model + CLI maduro

Sequential simple + plug-ins. CLI headless. Empaquetado como binario único.

Post-MVP

Paralelismo con cancelación jerárquica. Operator UI web. Editor visual. STDF/ATML. PyVISA nativo. StationGlobals. Custom step types.

Fin del MVP ≈ M5-base. LID (Legacy Isolation Domain) aplazado a post-M5-ext. Ver el roadmap completo.
