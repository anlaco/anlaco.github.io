Quick start

Your first step, in Python, in about twenty minutes.

By the end of this page you will have written a test step as an ordinary Python function, declared a sequence that runs it, and watched Anvil refuse to start a run because you mistyped a parameter name. No instrument, no rack time, no licence.

The one idea to carry through it. The step measures; the sequence judges. Your Python code never contains the pass/fail threshold, so tightening a tolerance is a text edit — not a recompile, not a redeploy, and not a phone call to whoever wrote the code.

What you need

  • Linux on x86-64. The binary is statically linked; there is nothing to install.
  • Python 3.10 or newer, with the standard venv module.
  • A clone of the Anvil repository — the Python executor lives there. You will not build it.

The Python executor is not yet packaged for download on its own; for now you copy two files out of the repository. That is a rough edge we know about, and it is the only part of this page that will get shorter.

Once, and never again

Set-up

Four commands. Everything lands in one folder you can delete when you are done.

01

Get the binary

One file, no runtime, no dependencies. It carries its own WebAssembly engine, which is why it weighs what it weighs and why it runs on a factory PC with no internet. 

mkdir anvil-quickstart && cd anvil-quickstart

# from github.com/anlaco/anvil/releases
tar xzf anvil-*-x86_64-linux-musl.tar.gz
./anvil --version

02

An isolated Python

A virtual environment is a folder with its own copy of Python. Nothing you install can break the Python your system uses. grpcio is how your steps and Anvil talk to each other. 

python3 -m venv venv
./venv/bin/pip install grpcio grpcio-tools

If this fails, delete the venv folder before retrying. A half-created environment is reused on the next attempt and fails again with the same message, which sends you looking in the wrong place.

03

Bring in the executor

server.py is the executor: the program that holds your steps and waits to be asked. You never edit it. anvil_step is the toolbox you import when writing a step. 

git clone https://github.com/anlaco/anvil.git
cp -r anvil/executores/python/anvil_step .
cp    anvil/executores/python/server.py  .

04

Generate the translators

Anvil and Python are written in different languages. A contract file defines the words they share, and this generates the Python side of it. The two paso_pb2*.py files are machine-written: never read, never edited, regenerated only if the contract changes. 

./venv/bin/python -m grpc_tools.protoc \
  -I anvil/crates/modelo \
  --python_out=. --grpc_python_out=. \
  anvil/crates/modelo/paso.proto

./venv/bin/python server.py --list
this executor serves no steps
(nothing found under the steps path)

That last line is success, not failure: the executor works and is telling you honestly that its catalogue is empty. You have not written a step yet.

Every day from now on

Write a step, run a sequence.

05

The step is a function

Put this in steps/my_steps.py. The decorator is the whole registration: no manifest, no config file, no list to keep in sync. 

from anvil_step import Result, step

@step
def measure_temperature(sensor: float) -> Result:
    """Reads the temperature of a sensor."""
    degrees = 20.0 + sensor
    return Result.measured(degrees, message=f"{degrees} C")

Every part of that signature tells Anvil something. sensor is the name a sequence will use; : float says it is a number; and having no default makes it required.

Note what is absent: nowhere does this code say whether 22.5 °C is acceptable. That is not the step's business.

06

The signature is the catalogue

Ask the executor what it serves. You wrote that description in exactly one place — the function — so it cannot drift from the code that runs. 

./venv/bin/python server.py --list

measure_temperature(sensor: number)
    Reads the temperature of a sensor.

Now start it and leave it running in a second terminal. It listens, and it reads your files once, at start-up — change a step, restart it. 

./venv/bin/python server.py
python executor listening on 127.0.0.1:9101 — 1 step(s)

07

The sequence is data

This is the file a test engineer writes and reviews — plain text, in a diff, with no programmer in the loop. Save it as hello.yaml. 

name: hello_bench

executors:
  - name: python
    type: grpc
    host: 127.0.0.1
    port: 9101

main:
  - name: measure_temperature
    executor: python
    inputs:
      sensor: 2.5
    limit:
      type: range
      min: 20.0
      max: 25.0

limit is the acceptance criterion, and it lives here rather than in the code. The day that instrument moves to another machine, only host changes.

08

Check before you measure

Anvil asks each executor what it serves and checks your sequence against the answer — once, before the first step. Mistype a name and see for yourself: 

./anvil hello.yaml --validate --with-executors

  - step 'measure_temperature' (python): it takes no
    input called 'sensorr' (it takes: sensor)
  - step 'measure_temperature' (python): the input
    'sensor' is required and the sequence does not send it

Without that check the run would have started, the executor would have dropped the unknown value, and the step would have measured something else and reported a pass. The message names the parameter you actually have, because the mistake is nearly always a typo.

--validate on its own reads and checks the file without connecting to anything, which is what makes it usable in CI with no hardware. --with-executors is the explicit opt-in for when they are up.

09

Run it

The verdict is also the exit code — 0 passed, anything else did not — so a sequence can gate whatever comes after it. 

./anvil hello.yaml

=== hello_bench: pass ===
  [pass] measure_temperature: 22.5 C

10

Now change the criterion, not the code

Set max: 22.0 in the YAML. Touch no Python. Do not restart the executor. Run it again: 

=== hello_bench: fail ===
  [fail] measure_temperature: …
$ echo $?
1

The step still measured 22.5 and still reported it happily. What changed is the verdict, and the detail line names the value it read and the range it was judged against.

That is the whole thesis in one edit. Whoever owns the tolerance can change it without owning the code — and the change is a line in a text file, with an author and a date, not a rebuilt binary nobody can diff.

From here: give a step several inputs, return extra named values that land in the report alongside the measurement, split a long sequence into reusable sub-sequences, or emit the results as JSON or CSV for whatever consumes them next. All of it is in the repository documentation.

The sequence is data. The step is a function.

Everything above runs on a laptop. When the instrument is real, only the body of the function changes.
